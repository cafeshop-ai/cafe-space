# Local API protocol v2 (draft)

Status: M1 local registry implementation; project admission, process supervision and adapters follow in their own M1 tasks. Rust types in `crates/protocol` are authoritative; `web/src/protocol/generated/` is produced by `ts-rs`. Run `cargo test -p cafe-space-protocol --locked` to regenerate those bindings; run `pnpm --dir web generate:protocol-fixtures` after editing examples. Rust tests validate the JSON examples in `fixtures/v2/`; TypeScript checks the same examples against the generated types. This daemon API is shared by desktop UI, CLI and remote browsers; it is separate from the legacy v0 host protocol v1. Cloud collaboration HTTP v1 and device-signaling contracts remain unchanged.

## Framing and validation

- Every transport exchanges the same logical frame: one UTF-8 JSON object, bounded by `MAX_FRAME_BYTES`. WebSocket text messages provide frame boundaries; Unix sockets, Windows named pipes and CLI IPC use a four-byte big-endian byte length. Binary WebSocket messages are rejected. Transport delimiters do not change the JSON payload or its byte limit.
- A frame is 1–262,144 bytes. Reject zero-length or oversized frames, invalid UTF-8/JSON, a second JSON value, duplicate fields, unknown fields and unsupported versions. Batches are not supported.
- Field names are `camelCase`; discriminator values are `snake_case`. IDs are non-empty, control-character-free and at most 128 UTF-8 bytes. Labels are at most 256 bytes; text is at most 65,536 bytes. Lists contain at most 1,000 entries, session views at most 1,000 messages and 64 approvals, and each message at most 500 parts. The encoded frame limit still applies to the whole message.
- Shared project/session types carry IDs and opaque fences, never paths, shell commands, environment variables or native agent IDs. Only local project administration accepts root paths, and only the local-only `get_project_root` response returns one over owner-only IPC. Shared lists, snapshots and events stay path-free. `cwdFence` and attach-target keys are not authorization credentials; the daemon must validate every operation independently. Capabilities only affect presentation, never authorization.

### Transport mappings

- **Current local socket/pipe runtime:** at most 32 active connections; a 5-second hello deadline; a 30-second deadline from the first byte of a frame until its body completes; a 30-second write deadline. There is one sequential reader/writer per connection. A framing error, timeout or cancellation closes that connection; partial frames are never resumed and unknown command outcomes are never retried. Established connections may wait idle between frames. Update events share one writer with responses. The handler retains an in-progress read while delivering events, rather than cancelling a partial frame. M0 keeps 64 replay events and a 64-event live queue per subscriber; a lagged subscriber is disconnected instead of silently skipping events.
- **WebRTC data channel:** carry binary packets on one reliable, ordered channel, reusing v0's `PCD1` chunk envelope (`relay/internal/remote/rtc.go` at `67237383fef260a8111a14910bc97a56195de349`). Each packet is at most 16,384 bytes: a 16-byte header of four big-endian `u32` values in the order **magic `0x50434431`, message ID, total frame bytes, byte offset**, followed by 1–16,368 payload bytes. Every frame uses this envelope, even when it fits one packet. Reassemble exactly one v2 UTF-8 JSON frame, with no socket length prefix; validate the total (1–262,144) before allocating. IDs start at 1 per direction and advance per complete frame, wrapping past zero to 1. Allow only one in-flight frame per direction, contiguous offsets starting at 0, and an unchanged ID/total until complete. Reject text packets, invalid bounds, gaps, overlap and replay. The first chunk sets a 10-second assembly deadline; later chunks do not extend it. The v0 decoder checks that deadline on the next `push`; v2 must also expire an idle partial frame. Close the transport on failure/expiry and release partial buffers. The reassembled frame goes through the same strict codec. Reusing this envelope does not change cloud signaling or permit a v2 hello to a v0 gateway.
- **Tauri IPC proxy:** a command argument carries one serialized client JSON frame string. A typed `Channel<DaemonDelivery>` carries a `message` wrapper with its connection ID, delivery sequence and decoded server message, or a `closed` wrapper. The Rust shell validates the frame and its UTF-8 byte length in both directions and only adds/removes the four-byte length prefix at the daemon socket/pipe boundary. The delivery wrapper and string escaping are not part of the logical frame-byte count. At most one delivery awaits acknowledgement; a missing acknowledgement closes the connection after five seconds. No token or IPC path enters JavaScript. The three-platform M0-5 native WebView spike confirmed this mapping (see `desktop/README.md`).

## Version handshake

Once a client has selected this API, each connection starts with a client hello before any request:

```json
{"type":"hello","supportedProtocolVersions":[2],"clientVersion":"0.1.0-dev"}
```

If a common version exists, the daemon replies with `type: "welcome"` and the selected `protocolVersion`, then accepts requests for that version. The daemon selects the highest common version. With no common version it sends `type: "version_mismatch"` and its `supportedProtocolVersions`, then closes the connection. A client or server supports 1–8 unique, nonzero versions in its offer; this daemon implements version 2 only. The `type: "request"`, `"response"` and `"event"` messages each carry `protocolVersion: 2`. The connection handler, not the stateless JSON codec, enforces that hello/welcome happens first.

Before opening a data channel, the remote compatibility layer reads the gateway's advertised host-protocol version. A v0 gateway selects legacy protocol v1 and must never receive a v2 hello. `version_mismatch` applies only after both peers implement this handshake.

## Requests and fencing

A request is `{ "type":"request", "protocolVersion":2, "requestId":"…", "request": { "method":"…", "params":{…} } }`. Unit methods omit `params`. Responses echo `requestId`; events have their own stream sequence.

| Method | Params | Result / semantics |
|---|---|---|
| `get_status` | — | Daemon health, readiness, `update` (`none`, `pending`, `draining`), optional `binaryHash` and per-boot `eventStreamId`. An uncommitted target reports `ready: false`, `awaitingUpdateConfirmation: true`; clients must explain unfinished handover rather than claim ready. Finish/rollback are native OS-controller operations (desktop or CLI), not daemon RPC methods. |
| `prepare_update` | `mode` (`now` or `when_idle`), `targetHash` | Local-only update lease and atomic admission gate; returns `kind: update`. |
| `cancel_update` | — | Local-only; cancels a pending lease owned by this connection. Draining cannot be cancelled. |
| `list_projects` | — | Approved project IDs, labels and `cwdFence`; no paths. |
| `add_project` | `root`, optional `name` | Local-only. Returns `kind: project` with a server-generated ID and fence; an already-approved directory identity returns its existing project. |
| `update_project` | `projectId`, `expectedCwdFence`, `root`, optional `name` | Local-only. Returns `kind: project`; changing root identity rotates the fence. Omitting name retains the label. |
| `remove_project` | `projectId`, `expectedCwdFence` | Local-only. Returns `kind: empty`; historical sessions remain, but cannot resume without their approved project. |
| `get_project_root` | `projectId` | Local-only. Returns `kind: project_root` with `projectId`, `cwdFence`, `root`. Never emitted as an event. |
| `list_runtimes` | — | Runtime profiles and availability. |
| `list_sessions` | — | Session summaries and an event cursor. |
| `subscribe_events` | optional `{ after: { eventStreamId, sequence } }` | Starts event delivery. Send an empty `params` object for a fresh snapshot; a valid cursor resumes. |
| `list_attach_targets` | `projectId`, `runtimeId` | Opaque attach keys; native IDs stay local. The target includes its `cwdFence`. |
| `get_session` | `sessionId` | Session view, bounded transcript/approvals and an event cursor. |
| `create_session` | client-chosen `sessionId`, `projectId`, `runtimeId`, `expectedCwdFence`, `start` | `start` is `{ "mode":"new" }`, `{ "mode":"resume", "params":{"sourceSessionId":"…"} }`, or `{ "mode":"attach", "params":{"targetKey":"…"} }`. Reusing the same `sessionId` and parameters returns its current durable view without another side effect; different parameters return `ID_CONFLICT`. Creation commits a `starting` record, not agent readiness. An unapproved project or unavailable runtime is rejected before insertion. |
| `open_session` | `sessionId`, `expectedStreamId`, `expectedCwdFence` | Idempotently opens/reconnects and returns the current view; stale fences reject it. |
| `set_model` | `sessionId`, `expectedStreamId`, `expectedCwdFence`, `provider` (≤128 bytes), `modelId` (≤256 bytes) | Changes the model when the adapter supports it; the daemon enforces capabilities and authorization. |
| `set_thinking` | `sessionId`, `expectedStreamId`, `expectedCwdFence`, `level` | `level` is `off`, `minimal`, `low`, `medium`, `high`, `xhigh` or `max`; the daemon checks adapter support. |
| `prompt` | `sessionId`, `expectedStreamId`, `expectedCwdFence`, `content`, `delivery` | `delivery` is `steer` or `follow_up`; a dispatched result is not completion. |
| `cancel` | `sessionId`, `expectedStreamId`, `expectedCwdFence`, `runId` | Cancels only the named run on that session; authorization is enforced by the daemon. |
| `respond_to_approval` | `sessionId`, `expectedStreamId`, `expectedCwdFence`, `approvalId`, `decision` | `decision` is `allow_once`, `allow_for_session` or `deny`; session-scoped approval requires adapter support. |
| `close_session` | `sessionId`, `expectedStreamId`, `expectedCwdFence` | Commits `stopping` and returns `dispatched` with the session stream as a stable operation ID. Repeated close during stopping returns the same dispatch without another transition. Only an observed process exit can produce `stopped`; closing an already terminal session returns its view without modifying it. Attached-agent detach follows with its adapter. |

`cwdFence` is an opaque per-project generation, rotated when its approved root changes. It is a stale-context check, not an authorization token. Create requests are fenced by the client-chosen session ID and the current project `cwdFence`. Operations against an existing session carry its `sessionId`, expected stream and expected cwd fence. The daemon rejects stale or mismatched fences before acting. Session summaries carry mode (`new`, `resume`, `attach`), state (`starting`, `ready`, `running`, `waiting_for_local_ui`, `stopping`, `stopped`, or `failed` with a code), the current cwd fence and stream ID, optional active run ID, current model/thinking level/title, and presentation-only capability flags (`modelControl`, `thinkingControl`, `deliveryControl`, `sessionControl`, `approvalForSession`). Clients use the active run ID for `cancel`; agent-native session IDs never leave the daemon.

A session snapshot may include `stopReason` **only** in `stopped` state. Its fixed codes are `DAEMON_RESTARTED`, `SESSION_CLOSED` and `AGENT_EXITED`; paths and exception text are never reasons. Restart recovery clears `activeRunId`, records `DAEMON_RESTARTED` for nonterminal sessions and never replays a prompt. Already stopped or failed sessions retain their terminal outcome. `failed` continues to use its own `data.code`, not `stopReason`. Lifecycle and fenced open/close examples are shared in `fixtures/v2/`.

`approvalForSession` only controls whether the UI offers **Allow for this session** (UX §6.3). It never grants permission: the daemon independently checks adapter support, authorization, fences and that the approval is still pending, rejecting an unsupported `allow_for_session` without applying it. The decision uses the agent's native session-scoped approval semantics, not persistent/global trust. The stateless codec accepts the wire value but cannot enforce these runtime checks. Resolution emits `approval_resolved` with the selected decision to clear the card on all devices; duplicate responses and unanswered/expired requests never auto-approve.

### Project administration (M1-2 contract)

The four local administration methods use transport-established `Access::Local`; a payload cannot declare its own access. Remote calls reject with `LOCAL_ONLY` before any caller-supplied path is inspected. The only path-bearing result is `project_root`, sent to that local caller, never to shared event subscribers. Errors and diagnostic logs contain fixed codes, not paths. Project labels are owner-visible choices that may be shared remotely: nonempty UTF-8, at most 128 bytes and no control characters; add defaults to the canonical directory's basename. Root input is valid UTF-8, nonempty, at most 65,536 bytes and control-character-free; native non-UTF-8 paths are rejected without lossy conversion.

The implementation must canonicalize existing absolute directories, resolve symlinks/junctions, and compare directory identity (Linux `statfs.f_fsid`/inode; macOS volume UUID/inode; Windows volume serial/128-bit FileId), not case-folded strings. Equivalent spelling retains the fence; a newly approved identity gets a random 128-bit fence. Unix device numbers are not persisted as identity because they may change after reboot/remount. Filesystems without a usable volume identity are rejected. A label-only update omits `root`, does not inspect the directory and retains the fence; an explicit `root` update reapproves its current identity. Reject volume/mount roots (including Linux bind mounts), daemon data-directory descendants and network filesystems (including UNC, mapped network drives, NFS and SMB). Missing or replaced roots fail closed until local approval; mutations are rejected while the project has a nonterminal session. Nested approved roots are allowed. Deleting then adding a directory creates a new project ID and fence, never reattaching old histories. This is a cwd allowlist, **not an OS sandbox**.

`project_changed` carries one `ProjectSummary`; `project_removed` carries only `projectId`. Both share the ordinary event cursor/replay rules, and update the project's client baseline. The offline arrays `project-requests.json` and `project-events.json` are independent-frame test traces, not wire batches.

**Current implementation boundary:** schema v3, local CRUD/root lookup, native directory identity checks, path-free shared snapshots/events and explicit CLI project commands are implemented. No project is automatically approved. Fresh session creates check the approved root, but still return `RUNTIME_UNAVAILABLE` because no runnable adapter is wired. The approved-cwd return value is for M1-3 spawn integration, which must recheck identity immediately before starting a child; this milestone does not claim a working agent or a closed TOCTOU window.

## Results

A response has exactly one status: `applied`, `rejected`, `dispatched` or `unknown`.

- `applied`: the operation finished and includes its typed result.
- `rejected`: the operation was not applied; includes a stable error code and display-safe message.
- `dispatched`: accepted for asynchronous work and includes an `operationId`; this is not a completion signal.
- `unknown`: the operation may have run, but its outcome cannot be proven. **Do not retry the command.** Reconcile by reading state; for creates, query the same client-chosen `sessionId` with `get_session` or `list_sessions`.

## Events, resume and snapshots

Events carry a daemon `eventStreamId` and monotonically increasing `sequence` from 1 to 1,000,000,000. A cursor may use sequence 0. The daemon rotates to a new `eventStreamId` before the sequence limit, and also on restart. Events cover session changes/removal, transcript messages, approval requests/resolutions, notices and `update_changed` (`data.update` is `none`, `pending` or `draining`).

`subscribe_events` atomically installs the live subscription and chooses one of two responses:

- `resumed`, with no snapshot, when `after` names the current stream and the daemon can replay every event after that cursor. The response's `(eventStreamId, sequence)` is the replay high-water mark; the daemon replays strictly increasing events through it, up to `MAX_REPLAY_EVENTS` (4,096), then continues live.
- `snapshot_required`, with a full snapshot, when no cursor was supplied, the stream changed, the cursor is ahead, or the missing range is unavailable/too large. The response's `(eventStreamId, sequence)` is the snapshot cursor. The subscription stays live; the daemon delivers later events strictly after that cursor.

The subscription response precedes replay/live event messages. The daemon installs the live queue before capturing either a snapshot cursor or a replay high-water mark. It sends the response, replays through that high-water mark when resuming, then delivers queued/live events; snapshot mode delivers events newer than its snapshot cursor. Clients apply only events newer than their last applied cursor; on a sequence gap or disconnect they subscribe again from that cursor. `get_session` and `list_sessions` also return their snapshot cursor for clients that fetch those views while subscribed. Model and thinking changes update the session snapshot and arrive as `session_changed` events.

A snapshot contains project, runtime and session summaries plus `update`; transcript history is fetched through `get_session`. Clients retain project, session and update baselines while replaying to the announced high-water mark. The desktop confirms health and the session list before requesting a subscription, so the subscription cursor cannot precede its list cursor. A single response or snapshot that cannot fit the frame limit is rejected with a stable size error. History may be truncated to fit and reports `historyTruncated`; pagination is deferred until adapter histories establish cursor semantics.

## Local daemon updates

Health optionally includes the current `eventStreamId` alongside `binaryHash`. The daemon publishes the same random per-boot stream ID and PID in the owner-only `daemon.instance` file before serving requests. The native updater checks both against its data directory (and the kernel pipe-server PID on Windows) before sending a mutating request. This stream ID is an identifier, not a credential or an authority grant. The record is separate from the mandatory Windows file-lock range so it remains readable while the daemon holds its single-instance lock.

`targetHash` and `binaryHash` use SHA-256: exactly 64 lowercase ASCII hexadecimal characters. Hashes describe binary integrity, not authority. The shell must stage and verify the bundled executable as a private `.next` file before preparing an update; the IPC layer never accepts a path from JavaScript. `prepare_update` for the already-running hash is a no-op, so a shell-only update does not stop agents.

`shutdown` is also local-only. The daemon freezes admission and checkpoints SQLite before replying with `shutdown_accepted`, then exits normally (code **0**) without writing an update marker. A lost reply is not replayed; the native caller reconciles the daemon lock. M0 has no agents; M1 must wire normal shutdown through the real agent registry before checkpointing.

Only a connection authenticated as local by the server can prepare or cancel an update; a request cannot declare itself local. A pending `when_idle` lease belongs to its originating connection. Normal work continues; connection loss cancels the lease. The daemon atomically checks idle and freezes admission under its state lock. `now` begins draining immediately. Draining rejects new work with `UPDATE_IN_PROGRESS` and cannot be cancelled, even if its originating connection disappears.

Before reporting draining, M0 checkpoints SQLite and durably writes `handover.json` with the old hash, target hash and phase. It replies with the update state, flushes `draining` to subscribed connections, and exits with code **42**. Subscriber shutdown gets at most five seconds; idle or non-reading clients cannot keep the old daemon alive indefinitely. Failed or lost replies are not retried: the native controller must reconcile the durable marker. A write with an uncertain outcome fails closed; it does not lift the admission barrier. Diagnostic log failures remain nonfatal and are distinct from critical state/marker failures.

An old daemon started by the OS records an unfinished handover as `not_applied`. A new target daemon stays fenced until the native controller records `committed`; it never initializes or migrates a schema during an uncommitted handover. A provisional target serves health but rejects session access. After commit it takes one private SQLite-API backup of the starting schema (including committed WAL pages), checks backup integrity, then applies all steps up to schema 3 in one transaction. Schema 2 adds the registry and `migration_history`; schema 3 adds projects. Every step has its own history row, all referencing that one backup; the marker records the overall from/to range. Private backups use `state.sqlite3.v<starting-version>.<random>.bak` and are not overwritten on retries. Migration provenance and completion are also recorded in a committed handover marker. A failed committed migration records `recovery_required`, retaining any backup metadata; subsequent boots refuse before opening SQLite instead of repeatedly backing it up. The live failed target still answers health with `ready:false`, omits `awaitingUpdateConfirmation`, and rejects work with `SCHEMA_MIGRATION_FAILED`. Local `shutdown` remains available so the native updater can stop it normally; remote shutdown remains `LOCAL_ONLY`. If persisting the recovery marker fails, admission stays fenced and only that marker write is retried on health polls, never the migration. Failed backup copies remove their `.writing` temporary file. `update finish` requires explicit restoration; `update rollback` can restore the old binary only if its read-only compatibility check accepts the current database. Neither command overwrites the database or backup. An interrupted committed attempt with a recorded backup but schema still at its starting version also requires recovery; completion after a crash is reconciled from the committed migration-history row only if the marker is not already `recovery_required`. The old binary's `--check-state` is a read-only compatibility check for rollback: it rejects a live daemon, nonempty WAL/hot journal, unknown schema/application ID or damaged database, and never replaces or migrates SQLite. After confirming no recovery data remains, it opens SQLite with `immutable=1` so even WAL/SHM sidecars are not created by the check. Native swapping, OS-manager startup and rollback are part of M0-6's shell integration, not evidence supplied by these backend tests alone. M0 has no agents; busy/idle tests use a `cfg(test)` hook absent from normal and release builds. Real busy-agent handover is still a required M1 verification.

### Native controller version requirement

Handover/recovery must use the CLI or desktop from the target daemon's source revision, or a newer compatible controller. Install/replace the controller first; the desktop embeds its target daemon from that checkout, and manual/headless installations must replace the CLI before the daemon. Whole-package updates and shell self-updates are not yet implemented, so mixed-version/manual installs are not automatically prevented. M0/schema-2 controllers reject schema-3 migration markers with `INSTALL_MARKER_INVALID`; recovery requires the current controller, not marker editing or deletion. The current controller may invoke the pinned old daemon's read-only compatibility check for rollback; that does not make the old controller compatible with a new marker.

## Scope

M1-1 adds durable session identity, create/open/close fencing, bounded snapshots and change events, and startup recovery of nonterminal records to `stopped(DAEMON_RESTARTED)` with no active run. Existing terminal outcomes are preserved. A single host mutex serializes admission, database changes, event sequencing and snapshots. Up to 1,000 sessions are retained; lists/snapshots that exceed the encoded frame limit return `RESPONSE_TOO_LARGE` rather than truncating silently.

Projects are approved only through explicit local administration. Without approval, fresh creates return `PROJECT_NOT_APPROVED`; with a valid approved root they still return `RUNTIME_UNAVAILABLE`, because **no runnable adapter** is wired. Synthetic runtime fixtures and observations exist only under `cfg(test)`; project methods cannot manufacture a ready session. Session views currently have empty transcript/approval collections. M1-3/4/5 must connect process observations and real adapters before public create/prompt/cancel completion is claimed. Normal shutdown and update stop-order tests still use the M0 synthetic gate until M1-3/8. Remote transport and remote authorization remain M2 work; session control here is local-only. Any future loopback WebSocket adapter requires a host allowlist, exact Origin and per-install token; the selected Tauri proxy does not open a loopback HTTP/WebSocket listener. Owner-only socket/pipe permissions remain transport responsibilities. Any implementation change to these semantics updates this document, Rust tests, generated TypeScript and the v2 examples together.
