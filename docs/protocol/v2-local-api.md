# Local API family v2 — full wire version 8

Status: M1 local registry implementation; project admission, process supervision and adapters follow in their own M1 tasks. Rust types in `crates/protocol` are authoritative; `web/src/protocol/generated/` is produced by `ts-rs`. Run `cargo test -p cafe-space-protocol --locked` to regenerate those bindings; run `pnpm --dir web generate:protocol-fixtures` after editing examples. Rust tests validate the JSON examples in `fixtures/v2/`; TypeScript checks the same examples against the generated types. This daemon API is shared by desktop UI, CLI and remote browsers; it is separate from the legacy v0 host protocol v1. Cloud collaboration HTTP v1 and device-signaling contracts remain unchanged.

## Framing and validation

- Every transport exchanges the same logical frame: one UTF-8 JSON object, bounded by `MAX_FRAME_BYTES`. WebSocket text messages provide frame boundaries; Unix sockets, Windows named pipes and CLI IPC use a four-byte big-endian byte length. Binary WebSocket messages are rejected. Transport delimiters do not change the JSON payload or its byte limit.
- A frame is 1–262,144 bytes. Reject zero-length or oversized frames, invalid UTF-8/JSON, a second JSON value, duplicate fields, unknown fields and unsupported versions. Batches are not supported.
- Field names are `camelCase`; discriminator values are `snake_case`. IDs are non-empty, control-character-free and at most 128 UTF-8 bytes. Labels are at most 256 bytes; text is at most 65,536 bytes. Lists contain at most 1,000 entries, session views at most 1,000 messages and 64 approvals, and each message at most 500 parts. The encoded frame limit still applies to the whole message.
- Shared project/session types carry IDs and opaque fences, never paths, shell commands, environment variables or native agent IDs. Only local project administration accepts root paths. Local-only `get_project_root` and `get_recovery_details` responses may return paths over owner-only IPC. Shared lists, snapshots and events stay path-free. `cwdFence` and attach-target keys are not authorization credentials; the daemon must validate every operation independently. Capabilities only affect presentation, never authorization.

### Transport mappings

- **Current local socket/pipe runtime:** at most 32 active connections; a 5-second hello deadline; a 30-second deadline from the first byte of a frame until its body completes; a 30-second write deadline. There is one sequential reader/writer per connection. A framing error, timeout or cancellation closes that connection; partial frames are never resumed and unknown command outcomes are never retried. Established connections may wait idle between frames. Update events share one writer with responses. The handler retains an in-progress read while delivering events, rather than cancelling a partial frame. M0 keeps 64 replay events and a 64-event live queue per subscriber; a lagged subscriber is disconnected instead of silently skipping events.
- **WebRTC data channel:** carry binary packets on one reliable, ordered channel, reusing v0's `PCD1` chunk envelope (`relay/internal/remote/rtc.go` at `67237383fef260a8111a14910bc97a56195de349`). Each packet is at most 16,384 bytes: a 16-byte header of four big-endian `u32` values in the order **magic `0x50434431`, message ID, total frame bytes, byte offset**, followed by 1–16,368 payload bytes. Every frame uses this envelope, even when it fits one packet. Reassemble exactly one v2 UTF-8 JSON frame, with no socket length prefix; validate the total (1–262,144) before allocating. IDs start at 1 per direction and advance per complete frame, wrapping past zero to 1. Allow only one in-flight frame per direction, contiguous offsets starting at 0, and an unchanged ID/total until complete. Reject text packets, invalid bounds, gaps, overlap and replay. The first chunk sets a 10-second assembly deadline; later chunks do not extend it. The v0 decoder checks that deadline on the next `push`; v2 must also expire an idle partial frame. Close the transport on failure/expiry and release partial buffers. The reassembled frame goes through the same strict codec. Reusing this envelope does not change cloud signaling or permit a v2 hello to a v0 gateway.
- **Tauri IPC proxy:** a command argument carries one serialized client JSON frame string. A typed `Channel<DaemonDelivery>` carries a `message` wrapper with its connection ID, delivery sequence and decoded server message, or a `closed` wrapper. The Rust shell validates the frame and its UTF-8 byte length in both directions and only adds/removes the four-byte length prefix at the daemon socket/pipe boundary. The delivery wrapper and string escaping are not part of the logical frame-byte count. At most one delivery awaits acknowledgement; a missing acknowledgement closes the connection after five seconds. No token or IPC path enters JavaScript. The three-platform M0-5 native WebView spike confirmed this mapping (see `desktop/README.md`).

## Version handshake

Once a client has selected this API, each connection starts with a client hello before any request:

```json
{"type":"hello","supportedProtocolVersions":[8],"clientVersion":"0.1.0-dev"}
```

If a common version exists, the daemon replies with `type: "welcome"` and the selected `protocolVersion`, then accepts requests for that version. The daemon selects the highest common version. With no common version it sends `type: "version_mismatch"` and its `supportedProtocolVersions`, then closes the connection. A client or server supports 1–8 unique, nonzero versions in its offer; current source implements full version 8 and frozen native control generation 2. Full-API `type: "request"`, `"response"` and `"event"` messages each carry `protocolVersion: 8`. The wire/schema-6 candidate remains pending native Rust, migration and pinned old-daemon acceptance; source definitions and synthetic fixtures do not prove those gates. The connection handler, not the stateless JSON codec, enforces that hello/welcome happens first.

### Frozen native update control (D18)

`crates/protocol/src/control.rs` separately validates control generation 2, whose wire version stays 2 when the full API advances. Its only methods are `get_status`, `prepare_update`, `cancel_update` and `shutdown`; responses are health, update or shutdown acceptance, or rejected/unknown errors. No subscriptions, session/project data, events or dispatched outcomes belong to this channel. `ControlClient` in `crates/ipc/src/client.rs` uses this codec, keeps the boot/hash (and Windows server-PID) checks, and refuses non-control calls before writing. Native installation/recovery uses that client; ordinary CLI requests retain the full-API client and strict current-version codec.

Once the full API advances beyond 2, a hello offering the current version selects the full API; otherwise an offer containing 2 selects control only. Other offers receive `version_mismatch`. The separate daemon control handler rejects unsupported methods, including unknown future methods, with `CONTROL_ONLY` before Host dispatch. Allowed methods still undergo strict shape, version, ID and hash validation. Pending updates retain the same connection lease, poll status rather than subscribe to events, and cancel on disconnect. The negotiated handler is covered by the frozen trace on the v3 daemon. An explicitly enabled isolated foreground probe also checks a separately built pinned protocol-2 binary; it never installs a service or replaces a user binary. These checks do not replace native OS-manager handover CI. `fixtures/control-v2/trace.json` remains unchanged.

Before opening a data channel, the remote compatibility layer reads the gateway's advertised host-protocol version. A v0 gateway selects legacy protocol v1 and must never receive a v2 hello. `version_mismatch` applies only after both peers implement this handshake.

`cwdFence` is an opaque per-project generation, rotated when its approved root changes. It is a stale-context check, not an authorization token. Create requests are fenced by the client-chosen session ID and the current project `cwdFence`. Operations against an existing session carry its `sessionId`, expected stream and expected cwd fence. The daemon rejects stale or mismatched fences before acting. Session summaries carry mode (`new`, `resume`, `attach`), state (`starting`, `ready`, `running`, `waiting_for_local_ui`, `stopping`, `stopped`, or `failed` with a code), the current cwd fence and stream ID, optional active run ID, current model/thinking level/title, and presentation-only capability flags (`modelControl`, `thinkingControl`, `deliveryControl`, `sessionControl`, `approvalForSession`) plus required `toolApproval` (`never_asks`, `may_ask`, `unknown`). The latter is an explicit profile/session policy, not inferred from runtime ID or the presence of a permission-request API. `may_ask` does not promise that every tool prompts; `unknown` makes no permission promise. Clients use the active run ID for `cancel`; agent-native session IDs never leave the daemon.

A session snapshot may include `stopReason` **only** in `stopped` state. Its fixed codes are `DAEMON_RESTARTED`, `SESSION_CLOSED` and `AGENT_EXITED`; paths and exception text are never reasons. Restart recovery clears `activeRunId`, records `DAEMON_RESTARTED` for nonterminal sessions and never replays a prompt. Already stopped or failed sessions retain their terminal outcome. `failed` continues to use its own `data.code`, not `stopReason`. Lifecycle and fenced open/close examples are shared in `fixtures/v2/`.

`approvalForSession` only controls whether the UI offers **Allow for this session** (UX §6.3). It never grants permission: the daemon independently checks adapter support, authorization, fences and that the approval is still pending, rejecting an unsupported `allow_for_session` without applying it. The decision uses the agent's native session-scoped approval semantics, not persistent/global trust. The stateless codec accepts the wire value but cannot enforce these runtime checks. Resolution emits `approval_resolved` with the selected decision to clear the card on all devices; duplicate responses and unanswered/expired requests never auto-approve.

### Session activity and preview (full wire v8)

`SessionSnapshot` has optional `lastActivityAt` and `preview`, visible locally and remotely on list/get, subscription snapshots and full `session_changed` events. Missing or null values mean unknown; canonical serialization omits them. A full snapshot replaces previous metadata, so an omitted preview clears the old preview. `lastActivityAt` is an integer Unix-millisecond timestamp from 1 through 8,640,000,000,000,000. Distinct live transcript observations, new session creation and actual lifecycle/configuration changes advance it using `max(previous, observed time)`; an invalid clock retains the previous value. Reads/open/reconnect, identical retries/observations, dispatch without observation, history hydration, migration and restart recovery do not manufacture activity.

`preview` contains only the latest observed native user's actual text, before display projection. Collapse Unicode whitespace, controls and bidi formatting U+202A..U+202E/U+2066..U+2069 to ASCII spaces, trim, then take the longest Unicode-scalar prefix within 256 UTF-8 bytes and trim trailing spaces. Empty text clears the preview. Nonempty wire previews must already be canonical; assistant/tool/system/thinking content is excluded. Native per-public-session insertion order chooses the newest user message, never lexical IDs or evictable cache row IDs; updates to older messages cannot replace newer previews. History can seed the preview without advancing time. Receipts and summaries survive display-cache eviction; transcript/provenance/metadata commit atomically, with events published only after commit.

Schema 6 leaves legacy metadata unknown. `fixtures/session-activity/{proposal,wire-v6,clock-examples,source-provenance}.json` pin bounds, provenance and clock behavior. Backend list order is unchanged; frontend #56 owns known-time descending/unknown-last sorting with ascending stable session-ID ties. This source contract does not imply native acceptance or permission to migrate user data.

### Configured model list (introduced in full wire v5, retained in v8)

`list_models` uses the existing `OpenSessionParams`. The Host checks transport-established local access, update/shutdown admission, current stream/cwd and approved directory identity before enqueue. It rechecks fences, readiness and directory identity on the correlated native result. Only `provider` (≤128 UTF-8 bytes) and `id` (≤256 bytes) are exported, without names, endpoints, headers, keys or costs. Invalid, oversized or duplicate lists fail as a whole. An empty successful list is `applied` with empty items; clients must not substitute a catalog.

The asynchronous IPC handler allows one pending model query per connection and continues reading requests and delivering events while it waits. A partial input frame survives both event and query-response delivery. Native rejection stays `rejected`; timeout, malformed native result or closed reply channel stays `unknown`. Enqueue/write completion is never `applied` or `dispatched`. A disconnected caller drops its receiver, not the native in-flight reservation; completion/timeout clears it without replay. All error strings are projected to fixed codes and messages. UI consumers must discard results for an obsolete session/fence and use authoritative model-change readback, never optimistic selection. This query does not enable production runtime admission; command controls use the separate local-only routing below.

### Model/thinking configuration (full wire v8)

Local-owner `set_model` and `set_thinking` use the shared native command admission and one pending configuration receiver per connection. The API continues health, events, close and disconnect while waiting. A mutation is `applied(empty)` only after a correlated mutation acknowledgement and a correlated `get_state` readback persisted into session state. The reply does not echo requested values; clients read authoritative state and discard obsolete session/fence results. Failed/missing readback is `unknown`, not rejection of an already acknowledged mutation. Explicit close preserves the native `PI_COMMAND_OUTCOME_UNKNOWN`; a dropped reply sender instead maps to `PI_CONNECTION_CLOSED`. Neither is success or permission to retry. Admission errors are fixed-code projections, not raw I/O text.

### Prompt, cancel and confirmation selection (full wire v8)

Local-owner prompt/cancel/confirmation selections use the native `command_pi` admission and correlated receivers. The handler retains at most 32 input replies per connection, with only cancel permitted to use the last slot. Ready replies carry their original request IDs without waiting for earlier inputs. Configuration retains its separate single slot; health, events, close and disconnect remain responsive. Dropping the connection drops receivers, not native commands, and never cancels or replays them. Initial errors are fixed-code projections.

Prompt/steer/follow-up native acceptance means dispatched, not turn completion. Cancel validates the owned `runId`, waits for `clear_queue`, rechecks the same run and sends abort only if still needed. Applied empty means settlement observed during clearing made abort unnecessary; it does not prove this request interrupted the run. Observed settlement remains authoritative regardless of response/event arrival order.

Pi confirmation selections support Allow once/Deny, not Allow for session. A public approval ID must belong to that session and still be pending. Dispatched requires complete writer flush, not enqueue, and is not native acknowledgement or tool permission. A real selected-decision event is emitted only while the dialog remains open. Unselected cancel/close/restart removes the authoritative dialog without inventing Allow/Deny. Unknown never retries; explicit close before writer observation preserves `PI_COMMAND_OUTCOME_UNKNOWN`, while a dropped sender maps to `PI_CONNECTION_CLOSED`. `toolApproval=never_asks` is unchanged.

`fixtures/pi-rpc/{commands,approvals}-wire-v5.json` precede this routing; Rust/TS shape checks and owned fake-process private IPC tests remain distinct from full desktop chat, real Agent admission and final-candidate cross-platform acceptance. The historically named fixtures now carry v8 envelopes. Frozen control-v2 and owner-settings v1 do not change; schema 6 adds activity metadata, and only explicitly registered Pi installations enter the runnable runtime list.

### Project administration (M1-2 contract)

The four local administration methods use transport-established `Access::Local`; a payload cannot declare its own access. Remote calls reject with `LOCAL_ONLY` before any caller-supplied path is inspected. Project administration returns paths only in `project_root`, sent to that local caller, never to shared event subscribers. Errors and diagnostic logs contain fixed codes, not paths. Project labels are owner-visible choices that may be shared remotely: nonempty UTF-8, at most 128 bytes and no control characters; add defaults to the canonical directory's basename. Root input is valid UTF-8, nonempty, at most 65,536 bytes and control-character-free; native non-UTF-8 paths are rejected without lossy conversion.

The implementation must canonicalize existing absolute directories, resolve symlinks/junctions, and compare directory identity (Linux `statfs.f_fsid`/inode; macOS volume UUID/inode; Windows volume serial/128-bit FileId), not case-folded strings. Equivalent spelling retains the fence; a newly approved identity gets a random 128-bit fence. Unix device numbers are not persisted as identity because they may change after reboot/remount. Filesystems without a usable volume identity are rejected. Windows extended prefixes are removed only for ordinary drive-letter paths and only if reopening the normalized path yields the original directory identity. Linux also rejects 9p, Ceph, AFS and Lustre; FUSE subtype lookup is bounded to 1 MiB of `/proc/self/mountinfo` and allows only `fuse.gocryptfs`, `fuse.ntfs-3g`, `fuseblk`, `fuse.bindfs` and `fuse.encfs`, rejecting unknown backends. A label-only update omits `root`, does not inspect the directory and retains the fence; an explicit `root` update reapproves its current identity. Reject volume/mount roots (including Linux bind mounts), daemon data-directory descendants and network filesystems (including UNC, mapped network drives, NFS and SMB). Missing or replaced roots fail closed until local approval; root edits/removal are rejected while the project has a nonterminal session, but label-only edits remain allowed. Adding an already recorded canonical path with a different identity returns `PROJECT_ROOT_CHANGED`; use an explicit `update_project` with `root` to reapprove that record. Nested approved roots are allowed. Deleting then adding a directory creates a new project ID and fence, never reattaching old histories. This is a cwd allowlist, **not an OS sandbox**.

`project_changed` carries one `ProjectSummary`; `project_removed` carries only `projectId`. Both share the ordinary event cursor/replay rules, and update the project's client baseline. The offline arrays `project-requests.json` and `project-events.json` are independent-frame test traces, not wire batches.

**Current implementation boundary:** schema v5 added private native-session identity mappings and a bounded normalized transcript cache after the explicit `toolApproval: "unknown"` v4 migration. Current source selects schema 6 for separate durable activity metadata and message receipts; the frozen wire-6 commit has same-SHA cross-platform migration and old-daemon refusal evidence, not acceptance of subsequent changes. Local CRUD/root lookup, native directory identity checks, path-free shared snapshots/events and explicit CLI project commands are implemented. No project is automatically approved. Native-only adapter tests own processes and persist lifecycle/transcript observations; wire session creation uses the registered Pi factory or returns `RUNTIME_UNAVAILABLE` when no valid profile exists. The cache retains at most 128 messages / 128 KiB of encoded message JSON per session; eviction or an omitted native record makes `historyTruncated` true. Native history remains authoritative. Failure/restart marks unfinished cached displays incomplete without inferring native execution outcomes or replaying commands. Private identity persistence alone is not a working Resume path: native history validation, fenced prompt/approval routing and owner settings remain separate gates. The cwd allowlist is not a sandbox.

### Pi runtime registration (full wire v8)

The owner chooses an existing absolute Node executable and the pinned Pi package directory through `cafe-space-dev runtime register pi <node> <package-directory>`. Requests carry only these two bounded UTF-8 paths (nonempty, at most 65,536 bytes each, no control characters), never arguments, environment or credentials. The daemon establishes local authority from IPC, rejects remote mutation before inspecting paths, passively checks the exact package name/version/CLI and persists canonical paths in owner-only `pi-runtime.json` version 1. Writes are atomic and durable; a failed or uncertain write is never retried automatically. `PI_RUNTIME_WRITE_UNKNOWN` requires reading `list_runtimes` before any explicit new decision. Lists and subscription snapshots export only `RuntimeSummary`. A damaged registration shows Pi as unavailable without hiding other snapshots. ### Recovery state (full wire 8, tasks #79/#81)

Full wire 8 distinguishes failed migration from ordinary update draining with typed, path-free health. The daemon and CLI use the same explicit restore contract; frozen control generation 2 never carries recovery fields or accepts recovery methods. UI acceptance remains separate from the backend fixtures.

- `get_status` gains an optional `recovery`, present only while the daemon refuses work because the state on disk needs local recovery, and absent otherwise:

  ```json
  { "code": "SCHEMA_MIGRATION_FAILED", "fromSchema": 5, "toSchema": 6, "backup": true }
  ```

  `code` is a fixed recovery code. Wire 8 has two: `SCHEMA_MIGRATION_FAILED` (a migration failed; the kept backup can be restored) and `ROLLBACK_REQUIRED` (the backup was restored; this daemon cannot run on it, so the owner goes back to the previous version). Any further code is a wire change. `fromSchema` and `toSchema` name the upgrade that failed. `backup` says whether the backup taken before the migration was kept, which is the restore source. The field carries no paths: every client may read health, including remote ones from M2.
- While `recovery` is present, `ready` is `false` and the daemon admits no session work. Clients show the recovery screen whatever `update` says.
- `get_recovery_details` (local owner only; remote clients get `LOCAL_ONLY`) returns what the screen lists: the data directory, the backup file and the state files involved, as local paths.
- Restoring is explicit, local and done by the daemon, which already holds the data-directory lock; no client touches the state files.
  - `restore_backup` (local owner only; remote clients get `LOCAL_ONLY`) carries `confirm: true` and the `code` it answers. It is valid only while `recovery.code` is `SCHEMA_MIGRATION_FAILED` and `backup` is true; otherwise it is rejected with `RESTORE_NOT_AVAILABLE`. The daemon replaces the state with a copy of the kept backup atomically and keeps the failed state beside it for diagnosis; it never deletes either. The result is truthful: `applied` once the restored state opened at `fromSchema` without migrating, `rejected` with a fixed code, or `unknown`.
  - The desktop app offers this as a button with an explicit confirmation, so desktop users never need a terminal. A headless host (Linux, D17) uses `cafe-space recovery status` and `cafe-space recovery restore`, which send the same request and ask for confirmation in the terminal.
  - With `backup: false` there is nothing to restore: the screen says so, asks the owner to keep the files untouched and to share `cafe-space status --json` with a maintainer. It offers no overwrite or unverified downgrade.
  - Under `SCHEMA_MIGRATION_FAILED`, restoring the backup remains the primary action. If the retained `.prev` passes a read-only check of a private copy of the **current data**, `rollbackAvailable` is true and the desktop also offers "go back to the previous version (data unchanged)" as a secondary action. A transactionally failed migration can therefore roll back directly, without restoring the backup first. If current data is incompatible, rollback returns `INSTALL_EXPLICIT_RESTORE_REQUIRED` when a retained backup exists, otherwise `INSTALL_ROLLBACK_STATE_REFUSED`.
- **After a restore the daemon never migrates again on its own.** The restored state is at `fromSchema`, which is exactly what the previous version can read. Running the failed migration again would upgrade it and take that way back away, and a deterministic failure would loop.
  - Owner-only `recovery.json` records phase, schema versions, failed binary hash, the validated backup basename, restored-copy hash and diagnostic basename. The daemon writes `restoring` before changing active state and `restored` only after opening the copied database read-only at `fromSchema`, with the expected application ID and passing integrity check. Diagnostic DB/WAL/SHM/journal bytes are retained before closing SQLite; active sidecars cannot contaminate the restored copy.
  - From then on `get_status` reports `{ "code": "ROLLBACK_REQUIRED", "fromSchema": 5, "toSchema": 6, "backup": true }` with `ready: false`, and the daemon admits no session work. `backup` still says whether the pre-migration backup file is kept; it is, since the restore copies it.
  - On every start with the latch present the daemon does not migrate and takes no new backup. With `restored`, it reports `ROLLBACK_REQUIRED`. With `restoring` (a crash during the restore), it requires retained failed-state evidence, the exact restored-copy hash, no nonempty sidecars, `fromSchema`, the expected application ID and a passing integrity check before recording `restored`; otherwise it records `failed` and reports `SCHEMA_MIGRATION_FAILED`. It never guesses completion from the schema number alone. The same latch, with phase `failed`, keeps a migration that failed without a handover marker from taking another backup on each start (M1-8).
  - The controller's "go back to the previous version" uses generated native `InstallationInfo.rollbackAvailable` under **both** recovery codes; on a headless host, use `cafe-space update rollback`. Availability requires a verified registration, the expected installed binary, a private retained `.prev`, and a successful `.prev --check-state` against an isolated private snapshot of the current data. The live daemon is not stopped and SQLite never opens its original database: only private copies of DB/WAL/journal are normalized into the snapshot. The controller verifies source hashes before and after copying/checking, snapshot hashes before and after the old-binary probe, plus latch, handover and executable hashes. `restored` additionally requires the recorded restored hash and no nonempty sidecars. Unavailable, incompatible or changed state means false. Without availability, the owner must explicitly arrange a compatible previous installation without overwriting data. Pre-wire-8 binaries ignore the retained latch.
  - Explicit rollback does not require an unfinished handover: after validating the retained executable, the controller can write its own recovery marker. It still stops through the OS manager and reruns the old binary's read-only check against the actual state before swapping executables (architecture §6). An interrupted binary swap with an existing marker remains resumable. Neither operation restores the database again.
  - While `recovery` is present, neither client nor controller offers "finish update": committing would run the failed migration again.
  - Direct rollback leaves the `failed` latch intact; rollback after restore leaves the `restored` latch intact. Updating again later is the explicit retry: only after successfully preparing a fresh draining handover does the controller record that old/target hash pair in either latch. Only that authorized handover, once committed, archives the latch before migration (`state.sqlite3.failed.<nonce>.recovery.json` when diagnostic state exists, otherwise a unique `recovery.<id>.json`). A stale starting/committed marker, finishing the old handover, and restarting the same daemon do not authorize a retry. An explicit restore revokes any previous retry authorization. A verified ready old daemon is not presented as still recovering merely because the evidence latch remains.

`recovery status --json` emits one ASCII-safe health result and, if recovery is present, one local details result as JSON lines. `recovery restore` requires an interactive terminal and the exact confirmation `restore`; there is no `--yes`, path override or automatic retry. A lost response stays unknown: read status before making another decision. Without a verified retained previous executable, binary rollback must be performed explicitly by the owner using a compatible previous installation; restore never installs an executable or clears the latch.

## Results

A response has exactly one status: `applied`, `rejected`, `dispatched` or `unknown`.

- `applied`: the operation finished and includes its typed result.
- `rejected`: the operation was not applied; includes a stable error code and display-safe message.
- `dispatched`: accepted for asynchronous work and includes an `operationId`; this is not a completion signal.
- `unknown`: the operation may have run, but its outcome cannot be proven. **Do not retry the command.** Reconcile by reading state; for creates, query the same client-chosen `sessionId` with `get_session` or `list_sessions`.

## Events, resume and snapshots

Events carry a daemon `eventStreamId` and monotonically increasing `sequence` from 1 to 1,000,000,000. A cursor may use sequence 0. The daemon rotates to a new `eventStreamId` before the sequence limit, and also on restart. Events cover session changes/removal, transcript messages, approval requests/resolutions, notices and `update_changed` (`data.update` is `none`, `pending` or `draining`).

`subscribe_events` atomically installs the live subscription and chooses one of two responses:

- `resumed`, with no snapshot, when `after` names the current stream and the daemon can replay every event after that cursor. The response's `(eventStreamId, sequence)` is the replay high-water mark; the daemon replays strictly increasing events through it, up to `MAX_REPLAY_EVENTS` (4,096), then continues live.
- `snapshot_required`, with a full snapshot, when no cursor was supplied, the stream changed, the cursor is ahead, or the missing range is unavailable/too large. The response's `(eventStreamId, sequence)` is the snapshot cursor. The subscription stays live; the daemon delivers later events strictly after that cursor.

The subscription response precedes replay/live event messages. The daemon installs the live queue before capturing either a snapshot cursor or a replay high-water mark. It sends the response, replays through that high-water mark when resuming, then delivers queued/live events; snapshot mode delivers events newer than its snapshot cursor. Clients apply only events newer than their last applied cursor; on a sequence gap or disconnect they subscribe again from that cursor. `get_session` and `list_sessions` also return their snapshot cursor for clients that fetch those views while subscribed. Model and thinking changes update the session snapshot and arrive as `session_changed` events.

A snapshot contains project, runtime and session summaries plus `update`; transcript history is fetched through `get_session`. Clients retain project, session and update baselines while replaying to the announced high-water mark. The desktop confirms health and the session list before requesting a subscription, so the subscription cursor cannot precede its list cursor. A single response or snapshot that cannot fit the frame limit is rejected with a stable size error. History may be truncated to fit and reports `historyTruncated`; pagination is deferred until adapter histories establish cursor semantics.

## Local daemon updates

Health optionally includes the current `eventStreamId` alongside `binaryHash`. The daemon publishes the same random per-boot stream ID and PID in the owner-only `daemon.instance` file before serving requests. The native updater checks both against its data directory (and the kernel pipe-server PID on Windows) before sending a mutating request. This stream ID is an identifier, not a credential or an authority grant. The record is separate from the mandatory Windows file-lock range so it remains readable while the daemon holds its single-instance lock.

`targetHash` and `binaryHash` use SHA-256: exactly 64 lowercase ASCII hexadecimal characters. Hashes describe binary integrity, not authority. The shell must stage and verify the bundled executable as a private `.next` file before preparing an update; the IPC layer never accepts a path from JavaScript. `prepare_update` for the already-running hash is a no-op, so a shell-only update does not stop agents.

`shutdown` is also local-only. The daemon freezes admission and checkpoints SQLite before replying with `shutdown_accepted`, then exits normally (code **0**) without writing an update marker. A lost reply is not replayed; the native caller reconciles the daemon lock. M0 has no agents; M1 must wire normal shutdown through the real agent registry before checkpointing.

Only a connection authenticated as local by the server can prepare or cancel an update; a request cannot declare itself local. A pending `when_idle` lease belongs to its originating connection. Normal work continues; connection loss cancels the lease. The daemon atomically checks idle and freezes admission under its state lock. `now` begins draining immediately. Draining rejects new work with `UPDATE_IN_PROGRESS` and cannot be cancelled, even if its originating connection disappears.

Before reporting draining, M0 checkpoints SQLite and durably writes `handover.json` with the old hash, target hash and phase. It replies with the update state, flushes `draining` to subscribed connections, and exits with code **42**. Subscriber shutdown gets at most five seconds; idle or non-reading clients cannot keep the old daemon alive indefinitely. Failed or lost replies are not retried: the native controller must reconcile the durable marker. A write with an uncertain outcome fails closed; it does not lift the admission barrier. Diagnostic log failures remain nonfatal and are distinct from critical state/marker failures.

An old daemon started by the OS records an unfinished handover as `not_applied`. A new target daemon stays fenced until the native controller records `committed`; it never initializes or migrates a schema during an uncommitted handover. A provisional target serves health but rejects session access. After commit it takes one private SQLite-API backup of the starting schema (including committed WAL pages), checks backup integrity, then applies all required steps up to the source-selected schema 6 in one transaction. Schema 2 adds the registry and `migration_history`; schema 3 adds projects; schema 4 adds explicit tool-approval policy; schema 5 adds private identities/transcript projection; schema 6 adds durable activity metadata and message receipts without backfilling legacy activity. Every step has its own history row, all referencing that one backup; the marker records the overall from/to range. Private backups use `state.sqlite3.v<starting-version>.<random>.bak` and are not overwritten on retries. Migration provenance and completion are also recorded in a committed handover marker. A failed committed migration records `recovery_required`, retaining any backup metadata; subsequent boots retain the recovery API without opening the active SQLite database or taking another backup. The live failed target still answers health with `ready:false`, omits `awaitingUpdateConfirmation`, and rejects work with `SCHEMA_MIGRATION_FAILED`. Local `shutdown` remains available so the native updater can stop it normally; remote shutdown remains `LOCAL_ONLY`. If persisting the recovery marker fails, admission stays fenced and only that marker write is retried on health polls, never the migration. Failed backup copies remove their `.writing` temporary file. `update finish` requires explicit restoration; `update rollback` requires a restored recovery latch when one exists, and can restore the old binary only if its read-only compatibility check accepts the current database. Neither command overwrites the database or backup. An interrupted committed attempt with a recorded backup but schema still at its starting version also requires recovery; completion after a crash is reconciled from the committed migration-history row only if the marker is not already `recovery_required`. The old binary's `--check-state` is a read-only compatibility check for rollback: it rejects a live daemon, nonempty WAL/hot journal, unknown schema/application ID or damaged database, and never replaces or migrates SQLite. After confirming no recovery data remains, it opens SQLite with `immutable=1` so even WAL/SHM sidecars are not created by the check. Native swapping, OS-manager startup and rollback are part of M0-6's shell integration, not evidence supplied by these backend tests alone. M0 has no agents; busy/idle tests use a `cfg(test)` hook absent from normal and release builds. Real busy-agent handover is still a required M1 verification.

### Native controller version requirement

Handover/recovery must use the CLI or desktop from the target daemon's source revision, or a newer compatible controller. Install/replace the controller first; the desktop embeds its target daemon from that checkout, and manual/headless installations must replace the CLI before the daemon. Whole-package updates and shell self-updates are not yet implemented, so mixed-version/manual installs are not automatically prevented. M0/schema-2 controllers reject schema-3 migration markers with `INSTALL_MARKER_INVALID`; recovery requires the current controller, not marker editing or deletion. The current controller may invoke the pinned old daemon's read-only compatibility check for rollback; that does not make the old controller compatible with a new marker.

## Scope

M1-1 adds durable session identity, create/open/close fencing, bounded snapshots and change events, and startup recovery of nonterminal records to `stopped(DAEMON_RESTARTED)` with no active run. Existing terminal outcomes are preserved. A single host mutex serializes admission, database changes, event sequencing and snapshots. Up to 1,000 sessions are retained; lists/snapshots that exceed the encoded frame limit return `RESPONSE_TOO_LARGE` rather than truncating silently.

Projects are approved only through explicit local administration. Without approval, fresh creates return `PROJECT_NOT_APPROVED`; with an approved root, a missing or invalid registered Pi installation returns `RUNTIME_UNAVAILABLE`. Project methods cannot manufacture a ready session. Native factory/owned fake-process tests produce bounded transcripts and confirmations and exercise local command IPC; registered Pi is selectable through the existing public create method. Authorized real-Agent and final desktop acceptance remain open. Native shutdown/update tests now use owned fake Agent processes and observed work rather than claiming real Agent acceptance from the M0 gate. Remote transport and remote authorization remain M2 work; session control here is local-only. Any future loopback WebSocket adapter requires a host allowlist, exact Origin and per-install token; the selected Tauri proxy does not open a loopback HTTP/WebSocket listener. Owner-only socket/pipe permissions remain transport responsibilities. Any implementation change to these semantics updates this document, Rust tests, generated TypeScript and the v2 examples together.
