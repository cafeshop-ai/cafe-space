## Launch and observation rules

- Invoke the absolute Node executable directly with the canonical CLI path, not a shell or Windows `.cmd` shim. Match v0's `--mode rpc --offline --no-extensions --no-approve --no-themes --session-dir ... --session-id ...`. No v0 collaboration extension is loaded. D20 now forwards the full daemon environment except CAFE_SPACE_*; ambient API keys and other owner variables inherit. M3 is out of scope.
- Host must provide an owner-only session directory, private native ID and the approved cwd identity, and own the resulting process. Resume validates the native ID/cwd/header and selects the exact native history file with `--session <canonical-file>`, not `--session-id` (which can create a missing conversation). It retains the same private ID/storage directory; missing identity/history is an error, never a new conversation disguised as Resume. No automatic replay or `--continue`.
- Startup is confirmed by a correlated `get_state` response with the expected private native ID and idle flags. The startup query is not a prompt; unexpected pre-prompt activity fails `PI_STARTUP_BUSY` rather than inventing a ready transition or accepting a different conversation. Once a run starts, only `agent_settled` is ready; `agent_end`, successful prompt responses and idle-looking intermediate queries do not complete a run. A `handled` prompt starts no run. This distinguishes initial readiness from run completion, because Pi emits no startup `agent_settled`.
- Consume strict LF-framed JSON objects continuously, accept CRLF, preserve U+2028/U+2029 and UTF-8 across read boundaries, and reject malformed bounded JSON or incomplete EOF with fixed codes. Oversized records are discarded through LF with a byte-counted placeholder; unknown/image blocks are represented by byte-counted placeholders. Assembled display overflow is explicitly truncated, not a session failure. Commands and dialogs remain bounded. Drain stderr separately without treating it as protocol or sharing raw diagnostics.
- Correlate responses by unique ID and command, not order. A successful prompt/steer/follow-up response is acceptance, not completion. A failed response is rejected with a fixed code, never the raw runtime error. EOF, write failure or a deadline leaves an unacknowledged command unknown; never retry automatically. Host owns deadlines, I/O scheduling, fences and caller/run ownership checks.
- A `confirm` dialog maps to explicit Allow once / Deny. Pi has no built-in tool-policy approval: do not infer permission semantics from arbitrary option labels. Generic `select`, `input` and `editor` require `waiting_for_local_ui`; the current v2 approval decision cannot carry free-form values. The `--no-extensions --no-approve` profile runs tools without asking. M1-6 must show “Runs tools without asking”, not a false approval toggle; `approval_for_session` is false. An oversized confirm request requires local UI rather than offering approval with hidden details. Writing an extension UI response is dispatched only, because Pi sends no acknowledgement.

### Native Host command routing (production disabled)

`Host::command_pi` is a local-owner Rust entry. The local full v5 API routes prompt/cancel/confirmation selections and configuration through asynchronous receivers; production runtime selection remains disabled. It validates the shared request codec, session/stream/cwd generations and approved directory identity before enqueue, returns a receiver for the correlated native outcome, and never treats an enqueue, writer completion or `agent_start` as command acceptance. Public operation/run IDs are random and independent of private native request IDs. Native startup enables the implemented Pi controls without inferring `toolApproval` from a runtime ID. Initial model metadata comes only from validated native state; model/thinking mutations require a subsequent correlated `get_state` readback before an applied result, preserving effective values even when native Pi clamps a requested level. Failed or missing readback is unknown, not rejection of the already-applied mutation.

First prompts are reserved against duplicate submission while awaiting native activity. Observed run start persists `activeRunId`; only observed settlement clears it as ready. Unowned activity fails closed. Active input maps to steer/follow-up with reordered replies independently correlated. Cancellation checks the owned run, awaits `clear_queue`, rechecks the current run and observed driver state, then sends `abort`; input remains blocked throughout the cancellation chain. Observations in each poll are persisted before command outcomes advance cancellation, so a run already observed settled is not aborted. Abort acknowledgement is dispatched, not turn completion. For a cancel request, `applied(empty)` specifically means `clear_queue` was acknowledged and the target run was already observed settled, so this request sent no abort; it must not be presented as proof that the request interrupted the run. `dispatched` means abort was acknowledged, with observed settlement still authoritative. `Ready` alone does not establish why a run ended. Host publishes the observed session state before resolving the command receiver, but this is not a transport-arrival guarantee: before M1-6 wire admission, test both response/event arrival orders and reconcile authoritative state without inferring cancellation causality from either. Model/thinking controls likewise display the read-back effective values, not the originally requested values. This uses the existing result kinds without a new protocol payload; richer per-request notices remain a separate protocol decision. Disconnect, malformed input, timeout and explicit close leave unacknowledged commands unknown without replay. An accepted prompt without any subsequent lifecycle event remains reserved until settlement or explicit close; no completion is invented.

The shared `host-commands.json` fixture drives owned fake-process cases for initial configuration, first/handled turns, reordered input acknowledgements, cancel/settlement races, stale run/stream/cwd fences, remote denial, effective model/thinking readback and rejected/missing readback, start without acknowledgement, duplicate reservation, failures and close with pending input. The local full-wire API admits configuration with the fixture-first `configuration-wire-v5.json` contract, and prompt/cancel use the command wire contract below. ### Native Host confirmations (production disabled)

Confirmations use the same local/stream/cwd/directory fences as commands. Host generates public random approval IDs rather than exposing per-adapter IDs or native dialog IDs, and `get_session` includes the current bounded confirmations at its event high-water mark. `approval_required` is published only after the in-memory view is updated. Retained encoded confirmation data is capped at 64 KiB per session; a request that cannot be offered in full requires local UI rather than silently truncating safety-relevant details or approving them. The driver is moved to the same local-UI state. Other generic select/input/editor requests also require local UI. These dialogs do not change the profile's truthful `toolApproval=never_asks` or create per-tool permission policy.

A selected Allow once or Deny resolves its shared native/wire receiver as `dispatched` only after complete writer flush, never merely after enqueue, and publishes `approval_resolved` with the real selected decision while the dialog is still open. Pi supplies no native acknowledgement. Duplicate pending selections and Allow for session are rejected before a second write. If settlement or failure closes the dialog before writer confirmation, a later complete-write observation can still report dispatched, but no fabricated decision event is added to the already-closed dialog. Unconfirmed writes remain unknown and are never replayed. Unselected dialogs closed by settlement, failure, explicit close or restart are simply absent from the authoritative snapshot; no Allow/Deny decision is invented. Claude's frontend reducer moves pending approvals to a bounded client-only expired list on authoritative ready/stopping/stopped/failed session changes; unanswered requests are shown as expired rather than silently disappearing, and sent replies are not mislabeled as unapproved. No approval state is resumed or executed after restart. Existing confirmation UI components are unchanged.

### Native Host Resume factory (production disabled)

`Host::start_installed_pi` accepts a trusted installation and local access only; callers cannot supply a native ID or Resume file. New sessions receive a private random native identity. Existing target IDs return their durable outcome without launching, revalidating/recreating history or replaying input. At most 4,096 native messages are projected into the newest 128 displays / 128 KiB encoded JSON, within the existing 1 MiB framed-record bound. The same adapter counter allocates history and subsequent live IDs, preventing overwrites. Host keeps `historyTruncated=true` because this is current context, not a complete pre-compaction archive. Rejected/malformed/timed-out history fails startup with fixed codes and owned cleanup; it sends no prompt and never retries. ### Native owner environment (historical checkpoint, superseded by D20)
